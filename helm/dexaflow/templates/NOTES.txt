{{- $preStopSleep := int .Values.deployment.preStopSleepSeconds }}
{{- if and (gt $preStopSleep 0) (ne (include "leoflow.preStopSleepHookSupported" .) "true") }}

WARNING: deployment.preStopSleepSeconds={{ $preStopSleep }} is set, but this apiserver ({{ .Capabilities.KubeVersion.Version }})
has no native preStop `sleep` action, so the chart rendered NO lifecycle hook and
the value has no effect. The action is gated on PodLifecycleSleepAction: beta and
on by default from Kubernetes 1.30, alpha and off in 1.29, absent before that.
The hook is omitted rather than rendered because an apiserver without the action
REJECTS the empty `preStop: {}` it is left with, which would fail this install
instead of dropping the sleep. So the install works and keeps the pre-hook
behavior: a terminating replica goes on accepting NEW agent log streams for the
endpoint-propagation window, and each one creates an empty log object for an
attempt whose lines then land nowhere. Move the control plane to 1.30+ to get the
sleep, or set deployment.preStopSleepSeconds=0 to stop asking for it.
{{- end }}
{{- if not .Values.taskNetworkPolicy.enabled }}

WARNING: taskNetworkPolicy.enabled=false — task pods have NO network containment.
Task pods run untrusted, author-supplied DAG code, and this chart always deploys
the production edition, so the network layer is where "a task can reach cloud
metadata, the apiserver, or any in-cluster service" is contained (ADR 0047/0048).
networkPolicy.enabled does NOT cover task pods: it selects control-plane pods in
namespace {{ .Release.Namespace }}, and its egress is a single empty rule
(- {}), which matches every destination — it restricts ingress only. Nothing
selects a task pod in namespace {{ .Values.taskNamespace }} until you set:
     --set taskNetworkPolicy.enabled=true
It is off by default on purpose, not by oversight: the policy always excludes
169.254.0.0/16 from its allow-all egress rule, and that is where GKE Workload
Identity and EKS Pod Identity serve
keyless credentials, so enabling it can break external-secrets auth until you
re-allow that one host with taskNetworkPolicy.allowMetadataEgress (a /32, e.g.
169.254.169.254/32 on GKE, 169.254.170.23/32 for EKS Pod Identity). Also
taskNetworkPolicy.blockPrivateNetworks=true additionally denies RFC1918 + the
apiserver; that one stays opt-in because a DAG calling an internal service is a
legitimate orchestration pattern. Both policies need a CNI that ENFORCES
NetworkPolicy — kindnet enforces nothing and the AWS VPC CNI enforces only with
its network-policy agent enabled, so a rendered policy is not proof of
enforcement. Verify on your CNI before relying on it.
{{- end }}
{{- /* Postgres connection budget (#1088). At boot pgxpool opens only its floor,
database.maxIdleConns, per pod, plus 3 (2 health checks, 1 scheduler leader lock);
under load each pod grows toward database.maxOpenConns + 3, plus
database.schedulerMaxConns on a pod that runs the scheduler (counted on every pod
here, an upper bound). Nothing scales either
by the replica count. The pod ceiling is the same one the logs PVC guard uses
(replicaCount, autoscaling.maxReplicas with the HPA on, split api + scheduler).
20 is the threshold: the smallest managed tiers cap max_connections near 25 and
reserve several of those. Boot demand over 20 is a WARNING (the pods may never
become ready); peak demand over 20 with more than one pod is an informational
NOTE, so a default single-replica install stays quiet. Notes, not a fail: the
chart cannot see the server's real max_connections. */ -}}
{{- $connPods := include "leoflow.logMounterCeiling" . | int }}
{{- $connJob := ternary 1 0 (.Values.migrations.enabled | default false) }}
{{- $connBoot := add (mul $connPods (add (int .Values.database.maxIdleConns) 3)) $connJob }}
{{- $connSched := int (.Values.database.schedulerMaxConns | default 0) }}
{{- $connPeak := add (mul $connPods (add (int .Values.database.maxOpenConns) $connSched 3)) $connJob }}
{{- $connSchedText := ternary (printf " + database.schedulerMaxConns=%d" $connSched) "" (gt $connSched 0) }}
{{- $connJobText := ternary " + 1 migration Job" "" (eq (int $connJob) 1) }}
{{- if gt (int $connBoot) 20 }}

WARNING: the control plane opens {{ $connBoot }} Postgres connections at boot:
  {{ $connPods }} pod(s) x (database.maxIdleConns={{ .Values.database.maxIdleConns }} + 3){{ $connJobText }}
(the 3 are each pod's health checks and scheduler leader lock). The smallest
managed tiers cap max_connections near 25 and reserve some of those; there the
pods fail to boot with SQLSTATE 53300. Lower database.maxIdleConns, run fewer
replicas, or use a larger server. See #1088.
{{- end }}
{{- if and (gt (int $connPeak) 20) (or (gt (int $connBoot) 20) (gt $connPods 1)) }}

NOTE: under load the control plane can grow to {{ $connPeak }} Postgres connections:
  {{ $connPods }} pod(s) x (database.maxOpenConns={{ .Values.database.maxOpenConns }}{{ $connSchedText }} + 3){{ $connJobText }}
Size the server's max_connections (minus its reserved slots) for that, or lower
database.maxOpenConns. See #1088.
{{- end }}

{{- if and .Values.auth.oidc.enabled (not .Values.auth.oidc.breakGlassEmails) }}

WARNING: auth.oidc.enabled with an EMPTY auth.oidc.breakGlassEmails. SSO is now
the only way into this install: every local password login is rejected, and the
break-glass list is the allowlist of the ones that are not. An IdP outage, an
expired client secret, or one wrong key in auth.oidc.tenantClaims therefore locks
out everybody, including the operator who has to fix it, and including the
audit log that would have said why (every rejection is a generic 403). Add at
least one address you control:
     --set auth.oidc.breakGlassEmails[0]=admin@example.com
{{- end }}
{{- if and .Values.auth.oidc.enabled (not .Values.auth.oidc.jitProvisioning) }}

WARNING: auth.oidc.enabled with auth.oidc.jitProvisioning=false. No SSO login
can succeed in this configuration. A login is matched to a user by the IdP's
(provider, subject) pair, and the only code path that ever writes those two
columns is the JIT one, so there is no account to match and every first login is
denied with a generic 403 whose reason (no_user_jit_off) reaches only the audit
log. Set auth.oidc.jitProvisioning=true (the chart default) unless you have
linked the identities yourself in the database.
{{- end }}
{{- if and .Values.auth.oidc.enabled (not .Values.auth.oidc.roleMappings) (not .Values.auth.oidc.defaultRole) }}

NOTE: auth.oidc has neither roleMappings nor defaultRole. Role resolution is
default-DENY, so an SSO login will succeed and then grant nothing, the user
lands in a UI that shows them no DAG and lets them do nothing, with no error to
explain it. Map the IdP groups you use (auth.oidc.roleMappings, remembering the
IdP's groups scope in auth.oidc.scopes), or set auth.oidc.defaultRole to a
read-only role such as `viewer` while you work that mapping out.
{{- end }}

{{- if .Values.migrations.enabled }}

Migrations run as a pre-install/pre-upgrade Job using image
"{{ .Values.migrations.image.repository }}:{{ .Values.migrations.image.tag | default .Chart.AppVersion }}",
which bundles the Dexaflow migrations at "{{ .Values.migrations.path }}"
(build/publish it with `make migrate-image`). Override migrations.image or set

Index migrations (0.5.1 ships eight) run CONCURRENTLY: each waits for every

in a window without long-running transactions. If the Job is interrupted, every
retry stops at "Dirty database version N. Fix and force version."; the recovery
runbook is at https://dexaflow.dexadata.ai/operate/upgrades/#an-interrupted-migration
